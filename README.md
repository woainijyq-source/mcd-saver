# 麦麦省钱助手

> 花最少的钱，吃得麦满意。

一个把你手里那些散落的麦当劳优惠券算清楚的工具。给它预算、口味偏好或者热量目标，
它告诉你**具体点什么、用哪张券、实付多少、省了多少**。

- 纯 Python 标准库，零第三方依赖
- 38 个回归测试，改算法前跑一遍就知道有没有算错钱
- 120 项菜单约 300 ms 出结果
- 可作为 WorkBuddy 技能使用，也可独立跑

---

## 它解决什么问题

每次点麦当劳，都会卡在这几个问题上：

- 手里四五张券，哪张最划算？
- 差 3 块就够满减门槛了，加个小食会不会反而更便宜？
- 预算 30 块，想吃饱，怎么配？
- 早餐券还有半小时过期，现在还来得及吗？
- 「板烧套餐 8 折」这张券，到底是只能买那个套餐，还是整单打折？

这些问题的答案都能算出来，但人算不过来——券有门槛、有时段、有渠道、有适用商品范围，
还要和套餐价格组合起来比较。**这个项目就是把这套算术做成确定性的代码。**

## 核心能力

### 1. 真的会凑单

这是整个项目最核心的一件事。

满减券的全部价值都在凑单：26 元的麦乐鸡够不到「满 30 减 5」，
但加一个 4 元薯饼凑到 30，实付变成 25 —— 比单点 26 还便宜 1 元，还白得一个薯饼。

引擎会主动找这种机会，也会判断什么时候**不该**凑（凑了反而更贵）。

```
1. [每元最扛饿] 双层吉士汉堡套餐 + 薯饼 + 迷你圆筒
   小计 ¥40.00 → 「满39免配送费」-¥9.00 + 配送 ¥9.00  = 实付 ¥40.00
   省钱 ¥9.00（18.4%）  |  1164 大卡  |  每元 29 大卡
   >>> 加 迷你圆筒（3 元）凑单，实付反而少 1.0 元
```

### 2. 券的规则全部建模

不是把规则写在提示词里指望模型记住，而是写成代码：

| 约束 | 处理方式 |
|---|---|
| 满减门槛 | 按商品小计算，不含配送费 |
| 折扣封顶 | 支持「8 折封顶 6 元」 |
| 适用商品 | SKU 白名单 + 品类白名单，板烧券不会拿去给薯条打折 |
| 时段 | 早餐券过了 10:30 自动失效 |
| 渠道 | 堂食 / 外带 / 麦乐送 分别判定 |
| 门店 | 门店专属券校验 store_id |
| 有效期 | 过期券直接排除并给出原因 |
| 叠加 | **一单只吃一张**，符合麦当劳实际规则 |

没用上的券会逐张说明理由：

```
未采用的券：
  - 早餐8折（10:30前）：仅 10:30 前可用
  - 满39免配送费：仅限麦乐送
  - 满25减4（已过期）：已于 2026-09-30 过期
```

### 3. 三种券型全覆盖

- 满减券（满 30 减 5）
- 折扣券（8 折封顶 6 元）
- 单品特价（双层吉士汉堡 15.9）
- 买一送一 / 第二份半价
- 免配送费

### 4. 多维推荐，不给一个假答案

「最便宜」「最划算」「省最多」是三件不同的事，硬压成一个答案必然误导。

默认给三个视角：

| 维度 | 含义 |
|---|---|
| 每元最扛饿 | 单位货币换到的热量最多，这才是「划算」的本义 |
| 实付最低 | 预算敏感时的底价解（已强制含主食） |
| 加几块升级 | 增量视角：多花 7.5 元能多吃 230 大卡 |

```bash
$ python3 scripts/cli.py --time 12:30 --budget 27 --want "麦乐鸡10块"

【围绕「麦乐鸡10块」的最优组合】
1. [每元最扛饿] 麦乐鸡10块 + 薯饼 + 甜酸酱
   小计 ¥30.50 → 「麦麦省 满30减5」-¥5.00  = 实付 ¥25.50
   省钱 ¥5.00（16.4%）  |  600 大卡  |  每元 24 大卡

2. [实付最低] 麦乐鸡10块
   小计 ¥26.00 → 「麦麦省 满20减3」-¥3.00  = 实付 ¥23.00
   省钱 ¥3.00（11.5%）  |  430 大卡  |  每元 19 大卡
```

## 快速开始

只需要 Python 3.10+，不用装任何东西。

```bash
git clone https://github.com/woainijyq-source/mcd-saver.git
cd mcd-saver

python3 scripts/cli.py                                   # 四个内置场景
python3 scripts/cli.py --budget 30 --time 12:30          # 30 元怎么点
python3 scripts/cli.py --budget 30 --calories-max 500    # 30 元内、500 卡以内
python3 scripts/cli.py --budget 30 --calories-min 700    # 30 元内要吃饱
python3 scripts/cli.py --want "麦乐鸡10块" --budget 27     # 想吃这个，帮我凑单
python3 scripts/cli.py --channel delivery --delivery-fee 9 --budget 45
python3 scripts/cli.py --budget 30 --json                # 机器可读
```

跑测试：

```bash
python3 -m unittest discover -s scripts/tests -t scripts -v
```

### 参数说明

| 参数 | 说明 |
|---|---|
| `--budget` | **实付**上限。凑单时小计可以超预算，只要券后实付达标 |
| `--calories-max` / `--calories-min` | 热量上下限。「要吃饱」用 min，不要用预算硬顶 |
| `--want` | 必须吃到的商品，支持中文模糊匹配，匹配到多个会要求写具体 |
| `--goal` | `min_pay` / `max_saving` / `best_value` / `max_ratio`，见下方警告 |
| `--channel` | `dine_in` / `takeaway` / `delivery` |
| `--time` | 当前时间，判断早餐券等时段券 |
| `--store` | 门店 ID，判断门店专属券 |
| `--addons` | 一个主体最多配几件补充品，默认 2 |
| `--json` | 输出 JSON 供程序或 Agent 消费 |

## 关于「省钱最多」这个陷阱

「省的钱最多」和「最划算」是两件事，很多人会混为一谈。

实测：预算是 30 元，两个方案

- A：实付 29.6，省 7.4
- B：实付 30.0，省 7.5

按「省钱最多」排序会选 B —— 用户多花 0.4 元，换来 0.1 元的「更多优惠」，**净亏 0.3 元**。

同理，「省钱比例最高」会把 24 元（11.1%）的方案换成 25 元（16.7%）的，
用户多花 1 元买了个更好看的折扣数字。

所以这两个目标只保留在 `--goal` 里供显式调用，不作为默认建议。

## 架构

```
SKILL.md                 WorkBuddy 技能定义
scripts/
  cli.py                 命令行入口
  mcd_saver/
    models.py            菜单、券、方案的数据模型（含主食判定）
    coupons.py           券的可用性判定与优惠计算
    optimizer.py         组合枚举 + 多目标优化（凑单能力在这里）
    loader.py            MCP 返回结构 -> 内部模型
  data/
    sample_menu.json     38 项演示菜单（含 0.5 元甜酸酱、4 元薯饼这类凑单神器）
    sample_coupons.json  10 张券，覆盖五种券型
  tests/
    test_optimizer.py    38 个回归测试
  benchmark.py           性能基准
references/
  mcp-tools.md           麦当劳 MCP 工具清单与调用要点
```

分层原则：**MCP 只负责取数，算法只负责算钱，提示词只负责对话。**
三件事混在一起写，等于把业务规则交给概率。

### 凑单是怎么枚举的

不是全组合暴力枚举（120 项菜单会爆炸），而是：

1. 每件商品单独点（含 2 份，用于买一送一）
2. 主体 + 1~2 件**低价候选池**里的补充品

再加两道剪枝：

- **小计上界 = 预算 + 单张券最大优惠能力** —— 超过这个数只会多花钱、不多省钱
- 只在通过预算/热量约束后才构造 Plan 对象

实测（`python3 scripts/benchmark.py`，5 张券、预算 60、最多 2 件补充品）：

| 菜单项数 | 候选组合 | 耗时 |
|---:|---:|---:|
| 40 | 6,931 | 55 ms |
| 80 | 24,914 | 179 ms |
| 120 | 41,230 | 298 ms |
| 200 | 73,860 | 539 ms |
| 400 | 155,434 | 1,212 ms |

单店真实菜单一般 80~150 项，也就是 0.2~0.4 秒。
菜单特别大时把 `--addons` 调成 1 可以砍掉一级组合，但凑单能力会下降。

## 接入麦当劳 MCP

引擎不负责取数。取数由 MCP 完成，然后把结果喂给 `loader`：

```python
from mcd_saver import menu_from_mcp, load_coupons_from_mcp, SearchConfig, recommend

menu = menu_from_mcp(mcp_result_of_query_meals)
coupons = load_coupons_from_mcp(mcp_result_of_query_my_coupons)

cfg = SearchConfig(budget=30, now_time=now, today=today)
for offer in recommend(menu, coupons, cfg):
    print(offer.headline, offer.plan.pay)
```

字段名做了宽容匹配（`sku` / `code` / `productCode` / `mealCode` 都认），
但**缺价格这类关键字段会直接抛 `DataError`**，不做静默兜底 —— 静默兜底最后一定算错钱。

MCP 配置见 `mcp-config.example.json`，Token 从 [open.mcd.cn/mcp](https://open.mcd.cn/mcp) 申请。
工具清单与常见坑见 `references/mcp-tools.md`。

## 能力边界

说清楚没做什么，比假装都有强：

- **套餐内商品替换**：`query-meal-detail` 返回的可替换项与加价规则尚未建模，需要时扩展 `MenuItem`。
- **起送价与配送范围**：只算配送费，没校验麦乐送起送门槛。
- **积分兑换省钱**：目前只能查积分余额。真正兑换需要 `mall-points-products` + `mall-create-order`，这两个没接。
- **活动日历**：`campaign-calendar` 没接。接入后可以做「本周活动 + 券叠加」。
- **历史订单对比**：`order-list` 没接。接入后能做「你上次这么点贵了 12 块」。
- **多份同品上限**：默认每 SKU 最多 2 份。多人点餐需要调高 `max_qty`，会让枚举变慢。

欢迎提 Issue 或 PR 补这些。
